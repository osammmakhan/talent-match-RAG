# Technical Requirements Document — Talent Match RAG

## 1. Architecture

```
data/candidates.json, data/jobs.json  (synthetic, generated by generate_synthetic_data.py)
        |
        v
sentence-transformers (all-MiniLM-L6-v2, local, free, 384-dim)
        |
        v
Pinecone (serverless, free tier, two namespaces: "candidates" and "jobs")
        |
        v
Retrieval: given a job, look up that job's stored vector in the "jobs"
namespace, then vector-similarity query for top-k candidates in "candidates"
(the model is not loaded at request time; see DECISIONS.md D13)
        |
        v
Augmented prompt: retrieved candidate text only, nothing invented
        |
        v
Groq (OpenAI-compatible endpoint, e.g. openai/gpt-oss-120b) generates
a short grounded rationale per candidate, under explicit guardrails
        |
        v
FastAPI returns similarity scores + rationale as JSON
        |
        v
React + TypeScript frontend: job picker, "Find Matches" button, result cards
```

## 2. Stack and rationale (see DECISIONS.md for full reasoning)

| Layer | Choice | Why |
|---|---|---|
| Embeddings | sentence-transformers, `all-MiniLM-L6-v2` | Free, local, no API key, no per-call cost |
| Vector store | Pinecone (serverless, free tier) | Fully managed, removes local-disk persistence problem on free hosting, most recognized vector DB in job postings |
| Generation | Groq (OpenAI-compatible API) | Free tier, fast inference, already a confirmed skill from prior personal projects |
| Backend | FastAPI | Already a confirmed skill (RomanUrdu.ai) |
| Frontend | React + TypeScript | React is a confirmed skill; TypeScript adds a legitimate, commonly paired keyword |
| Retrieval eval | Custom Python script, skill-overlap precision@5 | No framework needed, directly interpretable |
| Generation eval | OpenAI Evals framework, wired to Groq as the completion function | Real, checkable use of a recognized open-source eval framework, kept free by not calling OpenAI's paid API |

## 3. API contract

### GET /health
Returns `{"status": "healthy"}`.

### GET /jobs
Returns the full list of synthetic job postings.

### GET /candidates
Returns the full list of synthetic candidate profiles.

### POST /match/{job_id}?top_k=5
Runs the full RAG pipeline for one job.

Response:
```json
{
  "job_id": "job_001",
  "job_title": "Backend Engineer",
  "matches": [
    {
      "candidate_id": "cand_014",
      "similarity_score": 0.83,
      "rationale": "..."
    }
  ]
}
```

404 if `job_id` does not exist. 500 with an error detail if the pipeline fails (Pinecone or Groq call error).

## 4. Environment variables

| Variable | Purpose |
|---|---|
| `PINECONE_API_KEY` | Pinecone authentication |
| `PINECONE_INDEX_NAME` | Name of the serverless index (384-dim, cosine metric) |
| `GROQ_API_KEY` | Groq authentication |
| `GROQ_MODEL` | Generation model name, e.g. `openai/gpt-oss-120b` |
| `EMBEDDING_MODEL` | sentence-transformers model name, default `all-MiniLM-L6-v2` |
| `TOP_K` | Default number of candidates retrieved per match, default 5 |

## 5. Evaluation

### 5.1 Retrieval — precision@5 against a skill-overlap baseline
For every job, compute a baseline "relevant candidate" set using skill-overlap (candidate skills ∩ job required_skills, above a threshold). Compare Pinecone's actual top-5 retrieval against that baseline set and report the fraction of overlap. This is a proxy metric, not ground truth, and the README must say so explicitly.

### 5.2 Generation — groundedness check via OpenAI Evals + Groq
A custom eval (subclassing the Evals framework's base eval class) checks each generated rationale against the source candidate's actual skill list and flags any mentioned skill, tool, or experience claim not present in the source text. Completion function points at Groq, not OpenAI, so this stays free. Report the pass rate in the README.

## 6. Deployment

- Backend: Render, free web service tier. Because Pinecone is fully hosted, there is no local persistent-disk dependency — the backend calls Pinecone directly on every request.
- Frontend: Render static site or Cloudflare Pages, pointed at the deployed backend URL via an environment variable at build time.
- No database beyond Pinecone (vectors) and the static JSON files (source data) is required.

## 7. Explicitly out of scope for this phase

- Dockerfile and CI pipeline (deferred, see DECISIONS.md).
- Authentication, rate limiting, horizontal scaling, observability/monitoring stack.
- Hybrid (keyword + vector) retrieval and reranking — noted as a future extension only.

## 8. Constraints and risks

- Pinecone free tier: 2GB storage, up to 5 indexes, 1M reads / 2M writes per month — far more than this project's ~65-record dataset needs, but worth stating so scale limits are documented rather than assumed.
- Groq free tier has its own rate limits that can change; if the generation eval or live demo hits them, the fallback is to slow down request pacing, not to silently switch to a paid provider without updating this document and DECISIONS.md.
- sentence-transformers changes the embedding dimension from the original OpenAI-based MVP (1536 to 384) — the Pinecone index must be created with the correct dimension from the start, not migrated after the fact.
- Importing `sentence-transformers` costs roughly 414 MB of resident memory before any model is loaded, which does not fit Render's 512 MB free tier. This is why the request path retrieves stored job vectors instead of embedding (DECISIONS.md D13). Any future change that reintroduces an in-process embedding call will break the free-tier deploy.
